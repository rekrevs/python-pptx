# T-0022: Theme access API (color scheme, font scheme)

**Status**: READY | **Size**: L
**Phase**: PLANNING

## Context
Themes control the visual identity of a presentation (colors, fonts, effects). The XML is preserved on round-trip but completely inaccessible from Python. `CT_OfficeStyleSheet` exists (30 lines) as a stub in `src/pptx/oxml/theme.py`. A theme API would allow programmatic control over presentation styling — critical for template systems and AI-generated presentations.

Currently the theme part is loaded as a generic `Part` (not `XmlPart`) because `CT.OFC_THEME` is not registered in `content_type_to_part_class_map` in `src/pptx/__init__.py`. The `SlideMasterPart` has a `RT.THEME` relationship to this part but no `.theme` property or specialized part class exists.

### Anti-Pattern Warnings

**For this task specifically:**

1. **Theme part is currently generic `Part`, not `XmlPart`** -- The theme is loaded as `pptx.opc.package.Part` (blob only, no `.element`). Either register `CT.OFC_THEME` in `content_type_to_part_class_map` with a new `ThemePart(XmlPart)` class, or handle the blob-to-element conversion. The `ThemePart` approach is strongly preferred because it mirrors the pattern used for every other XML part in the project.

2. **`sysClr` vs `srgbClr` duality** -- The default theme uses `<a:sysClr val="windowText" lastClr="000000"/>` for dk1 and lt1, but `<a:srgbClr val="1F497D"/>` for others. The color reader must handle BOTH child element types. Using only `lastClr` from `sysClr` is acceptable for read (it gives the resolved RGB), but write should replace with `srgbClr` for portability.

3. **Do not test only with hand-crafted XML snippets** -- The existing `src/pptx/templates/theme.xml` contains a real-world default theme. Use it (or a copy) as a test fixture to ensure compatibility with actual PowerPoint output. Many edge cases (namespace prefixes, attribute ordering, optional elements) only appear in real files.

4. **Do not forget `_tag_seq` / `del _tag_seq` cleanup** -- The stub `CT_OfficeStyleSheet` has `_tag_seq` defined then deleted. When adding xmlchemy child descriptors (ZeroOrOne, OneAndOnlyOne), the `_tag_seq` must be preserved (not deleted) because the metaclass uses it for insert-order resolution. Removing the `del _tag_seq` line is required.

5. **Registration of new element classes** -- Every new CT_* class must be registered via `register_element_cls()` in `src/pptx/oxml/__init__.py`. Without registration, lxml will create generic `BaseOxmlElement` instances instead of the custom classes, and tests will silently pass while production code fails. Specifically register: `a:themeElements`, `a:clrScheme`, `a:fontScheme`, `a:majorFont`, `a:minorFont`, `a:fmtScheme`, and each color element (`a:dk1`, `a:lt1`, etc.) if needed.

6. **Don't break the existing `CT_OfficeStyleSheet.new_default()` test** -- The one existing test validates the default theme template round-trips. Modifying `CT_OfficeStyleSheet` (e.g. adding child descriptors) must not change the serialization of the default template.

7. **Don't mock the XML layer in API tests** -- Test with real parsed XML elements, not mocks. The xmlchemy descriptors have complex behavior (insert-before logic, namespace handling) that mocks cannot replicate. Use `element()` from `tests/unitutil/cxml.py` or `parse_xml()` to construct test fixtures.

8. **Color scheme has exactly 12 required children in a fixed order** -- Per the OOXML spec, `<a:clrScheme>` must contain exactly: dk1, lt1, dk2, lt2, accent1, accent2, accent3, accent4, accent5, accent6, hlink, folHlink. Tests should verify all 12 are accessible, not just a subset.

9. **Font scheme latin typeface is the primary one** -- `<a:majorFont>` and `<a:minorFont>` each contain `<a:latin>`, `<a:ea>`, `<a:cs>` and multiple `<a:font script="...">` children. The API should expose the `latin` typeface as the primary font name, since that's what most users want.

**Universal:**
- Run tests, don't just write them
- Check the full test suite, not just new tests
- Don't skip the linter on new files
- Verify the round-trip test actually opens the saved file (not just writes it)

### Research Summary

- `src/pptx/oxml/theme.py` -- Existing stub with `CT_OfficeStyleSheet` (30 lines). Has `_tag_seq` defined then immediately deleted. Contains `new_default()` classmethod that loads from template.
- `src/pptx/templates/theme.xml` -- Full default theme XML with clrScheme (12 color elements, mix of sysClr and srgbClr), fontScheme (majorFont/minorFont with latin/ea/cs), and fmtScheme.
- `src/pptx/oxml/__init__.py` -- Only `a:theme` is registered. No registrations for `a:themeElements`, `a:clrScheme`, `a:fontScheme`, `a:majorFont`, `a:minorFont`, `a:fmtScheme`, or color child elements (dk1, lt1, etc.).
- `src/pptx/oxml/dml/color.py` -- `CT_SRgbColor` has `val = RequiredAttribute("val", ST_HexColorRGB)`. `CT_SystemColor` exists but has no `lastClr` or `val` attribute exposed.
- `src/pptx/parts/slide.py` -- `SlideMasterPart` has no `.theme` property. `NotesMasterPart._new_theme_part()` creates theme as `XmlPart` (not a specialized part class). Theme is related via `RT.THEME`.
- `src/pptx/__init__.py` -- `content_type_to_part_class_map` does not include `CT.OFC_THEME`, so themes load as generic `Part` (blob only, no parsed XML element).
- `src/pptx/slide.py` -- `SlideMaster` extends `_BaseMaster` (extends `_BaseSlide` extends `PartElementProxy`). Has no `.theme` property.
- `src/pptx/shared.py` -- `PartElementProxy` wraps element+part. `ElementProxy` wraps just an element. These are the standard proxy base classes.
- `src/pptx/oxml/xmlchemy.py` -- `OneAndOnlyOne`, `ZeroOrOne`, `ZeroOrMore`, `RequiredAttribute`, `OptionalAttribute` are the declarative descriptors. `_tag_seq` must be preserved for insert-order resolution.
- `src/pptx/oxml/text.py` -- `CT_TextFont` has `typeface = RequiredAttribute("typeface", ST_TextTypeface)` -- this is the pattern for font element classes.
- `src/pptx/dml/color.py` -- `RGBColor` is an immutable tuple subclass with `from_string(hex_str)` classmethod and `__str__` returning hex. `ColorFormat` is for fill/font colors (unrelated to theme scheme colors).
- `src/pptx/oxml/simpletypes.py` -- `XsdString` is the base string type for `name` attributes. `ST_HexColorRGB` validates 6-char hex strings.

**Relevant prior work:**

- `CT_OfficeStyleSheet` test in `tests/oxml/test_theme.py` validates `new_default()` via snippet comparison.
- `tests/test_files/snippets/default-theme.txt` contains the expected serialized XML for the default theme.

### Approaches Considered

#### 1. Three-Layer Architecture: OXML + ThemePart + API Proxies (P = 0.85)

**Description**: Follow the established Chart/Presentation pattern with three clean layers:
- **OXML layer** (`src/pptx/oxml/theme.py`): Extend `CT_OfficeStyleSheet`, add `CT_BaseThemeElements`, `CT_ColorScheme`, `CT_FontScheme`, `CT_FontCollection`, and per-color element classes (e.g. `CT_ThemeColor` for dk1/lt1/etc.)
- **Part layer** (`src/pptx/parts/slide.py`): Add `ThemePart(XmlPart)` in the existing slide parts module, register in content_type_to_part_class_map, add `.theme_part` property to `SlideMasterPart`
- **API layer** (`src/pptx/theme.py`): New module with `Theme(PartElementProxy)`, `ColorScheme(ElementProxy)`, `FontScheme(ElementProxy)`

The color scheme colors would each be a "color slot" element (`a:dk1`, `a:lt1`, etc.). Since these all have the same structure (a single child that is either `srgbClr` or `sysClr`), a single `CT_ThemeColor` class registered for all 12 tag names works. Each color slot provides helper methods to read/write the color value.

The `ColorScheme` API class exposes 12 named properties (`.dark1`, `.light1`, `.accent1` etc.) plus iteration. Reading extracts the hex value from either `srgbClr/@val` or `sysClr/@lastClr`. Writing replaces the child with `srgbClr`.

The `FontScheme` API class exposes `.major_font` and `.minor_font` as string properties backed by the `latin/@typeface` attribute of the corresponding `CT_FontCollection`.

| Criterion | Score | Notes |
|-----------|-------|-------|
| Pattern alignment | + | Matches Chart (Part+API proxy), existing xmlchemy patterns |
| Elegance | + | Clean separation of OXML/Part/API layers |
| Surface area | - | ~6 files modified/created (oxml/theme.py, parts/slide.py, theme.py, __init__.py x2, slide.py) |
| Risk | + | Low -- follows proven patterns, no architectural novelty |
| Testability | + | OXML tests with parsed XML, API tests with element fixtures, BDD with real .pptx |
| Reversibility | + | New module + minimal additions to existing files |

**Pros**: Best pattern alignment. Each layer is independently testable. `ThemePart` registration means themes get parsed XML on load automatically. Proxy pattern is idiomatic to the project.
**Cons**: More files touched than a minimal approach, but each change is small and focused.

#### 2. Flat OXML + Inline API on SlideMaster (P = 0.65)

**Description**: Skip the separate `theme.py` API module. Instead, extend `CT_OfficeStyleSheet` with convenience methods that directly return `RGBColor` values and font names. Add the color/font access methods directly to `SlideMaster` in `src/pptx/slide.py`, delegating to the OXML element methods. No separate `Theme`, `ColorScheme`, `FontScheme` proxy classes.

| Criterion | Score | Notes |
|-----------|-------|-------|
| Pattern alignment | - | Violates proxy pattern used everywhere else in project |
| Elegance | - | Mixes XML manipulation with business logic |
| Surface area | + | Fewer files (~3-4) |
| Risk | + | Lower complexity |
| Testability | - | Harder to test API independently of OXML |
| Reversibility | - | Logic embedded in SlideMaster is harder to extract later |

**Pros**: Fewer files, simpler initial implementation.
**Cons**: Anti-pattern for this project. Every other feature (Chart, Slide, Shape) uses the Part+Proxy separation. Breaking this pattern would make the codebase inconsistent. Also loses composability -- you can't pass a `ColorScheme` object around independently.

#### 3. Full OXML + ThemePart But No Separate API Module (P = 0.72)

**Description**: Same OXML and ThemePart layers as Approach 1, but instead of a separate `src/pptx/theme.py`, put the `Theme`, `ColorScheme`, and `FontScheme` classes directly in `src/pptx/slide.py` alongside `SlideMaster`. This reduces file count but keeps the proxy pattern.

| Criterion | Score | Notes |
|-----------|-------|-------|
| Pattern alignment | ~ | Proxy pattern preserved, but module organization diverges (Chart has its own module) |
| Elegance | - | `slide.py` is already 686 lines; adding theme classes makes it bloated |
| Surface area | + | One fewer file |
| Risk | + | Low technical risk |
| Testability | + | Same as Approach 1 |
| Reversibility | ~ | Would need extraction later as theme features grow |

**Pros**: One fewer file to create.
**Cons**: `slide.py` already has 10+ classes. Theme is a distinct concept that deserves its own module (like Chart has `chart/chart.py`). Future theme features (effects, background styles) would make this worse.

#### 4. Separate theme/ Package (P = 0.70)

**Description**: Create a `src/pptx/theme/` package directory (like `chart/`, `dml/`, `oxml/`) with `__init__.py`, `theme.py`, `colorscheme.py`, `fontscheme.py`. More modular but more structure than needed for the current scope.

| Criterion | Score | Notes |
|-----------|-------|-------|
| Pattern alignment | ~ | Chart uses a package, but chart has many more submodules |
| Elegance | - | Over-engineered for current scope (3 small classes) |
| Surface area | - | More files, more imports to manage |
| Risk | ~ | Low technical risk but unnecessary complexity |
| Testability | + | Same as Approach 1 |
| Reversibility | + | Easy to refactor to/from single module |

**Pros**: Maximum modularity, room to grow.
**Cons**: Over-engineered. Chart needs a package because it has 10+ modules. Theme currently needs 3 classes. A single `theme.py` module is the right size. Can always promote to a package later if needed.

#### 5. Register Per-Color Element Classes vs. Single Shared Class (Sub-decision within Approach 1) (P = 0.85)

This is a design sub-choice that affects all approaches:

**Option A: Single `CT_ThemeColor` class registered for all 12 tags** (dk1, lt1, dk2, lt2, accent1-6, hlink, folHlink). Each tag name maps to the same class, which provides `rgb_color` read/write access by inspecting its child (srgbClr or sysClr).

**Option B: No custom class for individual color elements; handle in `CT_ColorScheme`**. Use `lxml.find()` to locate children by tag, then inspect their sub-elements directly. Color elements stay as generic `BaseOxmlElement`.

Option A is cleaner -- it gives each color slot element a proper type with typed property access. Option B requires more manual XML manipulation in `CT_ColorScheme`. The task specification explicitly calls for registering color elements "if needed," and since we need to read/write their children, Option A is warranted. However, the 12 child tags are essentially structurally identical (each contains exactly one color choice element), so a single class is appropriate.

### Recommendation

**Selected**: Approach 1 -- Three-Layer Architecture: OXML + ThemePart + API Proxies

**Rationale**:
- Highest confidence (P = 0.85) due to strong alignment with every other feature in the codebase
- Clean three-layer separation (OXML / Part / API) matches Chart, Diagram, and other established patterns
- Each layer is independently testable, aligning perfectly with the verification plan's separate test files
- `Theme(PartElementProxy)` naturally mirrors `Chart(PartElementProxy)`
- `ColorScheme(ElementProxy)` and `FontScheme(ElementProxy)` follow `Legend(ElementProxy)` etc.
- A dedicated `src/pptx/theme.py` module is the right granularity -- not too little (inline), not too much (package)

Design decisions:
- Color scheme properties use Python-friendly names: `dark1`, `light1`, `dark2`, `light2`, `accent1`-`accent6`, `hyperlink`, `followed_hyperlink` (mapped from XML dk1, lt1, dk2, lt2, accent1-6, hlink, folHlink)
- Color reading: `srgbClr` -> `RGBColor.from_string(val)`, `sysClr` -> `RGBColor.from_string(lastClr)`
- Color writing: Always replace child with `srgbClr` (removes sysClr if present) for portability
- Font scheme: `.major_font` and `.minor_font` return/accept string typeface names from `latin/@typeface`
- `CT_ThemeColor` -- single class registered for all 12 color slot tags, with `rgb_color` property
- `ThemePart.theme` lazyproperty returns `Theme(self._element, self)` following `ChartPart.chart` pattern
- `SlideMasterPart.theme_part` returns `self.part_related_by(RT.THEME)` following `SlidePart.slide_layout` pattern

**Fallback**: If `ThemePart` registration causes issues with `NotesMasterPart._new_theme_part()` (which currently creates `XmlPart` directly), update that method to use `ThemePart` instead. This is a one-line change and should be safe since `ThemePart` extends `XmlPart`.

### Design Decisions

**Single CT_ThemeColor class for all 12 color slots**: All 12 color slot elements (dk1, lt1, dk2, lt2, accent1-6, hlink, folHlink) share identical structure (single color child), so one class registered for all 12 tags is appropriate.

**Color reading handles both srgbClr and sysClr**: The `rgb_color` property reads from `srgbClr/@val` first, then falls back to `sysClr/@lastClr`. Writing always replaces with `srgbClr` for portability.

**Python-friendly property names on ColorScheme**: Maps `dark1`/`light1`/`hyperlink`/`followed_hyperlink` to XML `dk1`/`lt1`/`hlink`/`folHlink`.

**ThemePart registration**: Theme parts are now loaded as ThemePart(XmlPart) instead of generic Part, enabling parsed XML element access.

**Reuse of existing "I save and reload the presentation" BDD step**: Avoided duplication by using the existing step from `features/steps/presentation.py`.

### Alignment

- `Theme(PartElementProxy)` mirrors `Chart(PartElementProxy)` pattern
- `ColorScheme(ElementProxy)` and `FontScheme(ElementProxy)` follow `Legend(ElementProxy)` pattern
- `ThemePart(XmlPart)` follows `ChartPart(XmlPart)` pattern
- `SlideMasterPart.theme_part` follows `SlidePart.slide_layout` relationship pattern
- All element classes use xmlchemy descriptors (OneAndOnlyOne, ZeroOrOne, RequiredAttribute, OptionalAttribute)
