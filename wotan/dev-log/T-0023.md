### Anti-Pattern Warnings

**For this task specifically:**

1. **Do not break the existing `ShadowFormat.inherit` behavior.** The `inherit` property and its XML semantics (presence/absence of `a:effectLst`) are the foundation. New properties must coexist with this model. When `inherit` is True (no effectLst), read-only property getters should return None to indicate "inherited/unknown".

2. **Do not test with mocks where XML fixtures suffice.** The existing `test_effect.py` uses the `cxml` mini-language (e.g., `element("p:spPr/a:effectLst")`) to create real XML elements. Follow this pattern. The cxml language supports attributes: `a:outerShdw{blurRad=40000,dist=23000,dir=5400000}`.

3. **Remember the "all-or-nothing" inheritance model.** Per `shp-shadow.rst`, if `a:effectLst` is present, ALL desired effects must be specified explicitly. Do not add setter methods that naively add a single effect element without considering this constraint. Getters are safer to implement first.

4. **Angle units are 60000ths of a degree.** The `dir` attribute on `a:outerShdw` uses EMU-style angle units (60000 per degree). Use `ST_PositiveFixedAngle` simple type which handles the conversion. Do not hand-roll angle conversion.

5. **`blurRad`, `dist`, and `rad` are EMU values (ST_PositiveCoordinate).** These are returned as `Emu` instances via `ST_PositiveCoordinate.convert_from_xml`. Do not return raw integers.

6. **Color access requires a color child element.** `a:outerShdw`, `a:innerShdw`, and `a:glow` all require exactly one color child (EG_ColorChoice). When no shadow element exists, `.color` should raise or return a sensible default. Study how `LineFormat.color` delegates to `FillFormat` and `ColorFormat`.

7. **Do not forget to register new OXML element classes in `src/pptx/oxml/__init__.py`.** Every CT_* class needs a `register_element_cls("a:tagname", CT_ClassName)` call, or lxml will use generic `_Element` instead of the custom class, and attribute/child access via xmlchemy descriptors will silently not work.

8. **GraphicFrame.shadow already raises NotImplementedError.** Do not add `glow`, `reflection`, `soft_edge` to GraphicFrame without also raising NotImplementedError, maintaining consistency.

9. **BDD test file (`dml-effect.pptx`) must be updated.** The acceptance test fixture file at `features/steps/test_files/dml-effect.pptx` currently has two shapes (index 0: inherits shadow, index 1: does not inherit). New shapes must be added with explicit shadow/glow/reflection/soft-edge effects. Use PowerPoint or python-pptx itself to create these test shapes.

10. **Do not confuse `a:effectLst` with `a:effectDag`.** The `effectDag` is a directed acyclic graph of effects used for complex compositions. This task should only handle `a:effectLst` (the simple list). The schema in CT_ShapeProperties already declares both as a ZeroOrOneChoice, but only `effectLst` is declared; `effectDag` should remain unsupported.

**Universal:**
- Run tests, do not just write them
- Check the full test suite, not just new tests -- regressions from modifying shared base classes are the primary risk
- Do not skip type checking: new code should not introduce pyright errors beyond pre-existing ones
- Verify that existing BDD scenarios in `features/dml-effect.feature` still pass after changes

- `src/pptx/shapes/base.py:182` -- `BaseShape.shadow` returns `ShadowFormat(self._element.spPr)` via `@lazyproperty`.
- `src/pptx/shapes/group.py:44` -- `GroupShape.shadow` returns `ShadowFormat(self._grpSp.grpSpPr)` via `@lazyproperty`.
- `src/pptx/shapes/graphfrm.py:94` -- `GraphicFrame.shadow` raises `NotImplementedError`.
- `src/pptx/oxml/shapes/shared.py:345-397` -- `CT_ShapeProperties` declares `effectLst = ZeroOrOne("a:effectLst", ...)` but no custom `CT_EffectList` class exists; it defaults to `BaseOxmlElement`.

- `src/pptx/dml/color.py` -- `ColorFormat.from_colorchoice_parent(elm)` accesses `elm.eg_colorChoice` to create a `ColorFormat`. The shadow/glow elements contain an `EG_ColorChoice` group (exactly one color child element).
- `src/pptx/oxml/dml/color.py` -- `_BaseColorElement` has `lumMod`, `lumOff`, `alpha` children. `CT_SolidColorFillProperties` uses `eg_colorChoice = ZeroOrOneChoice(...)` pattern, the same pattern needed for outer shadow, inner shadow, and glow elements.
- `src/pptx/oxml/simpletypes.py` -- `ST_PositiveCoordinate` (EMU values, returned as `Emu`), `ST_PositiveFixedAngle` (60000ths of degree, converted to float degrees), `ST_Angle` (same). Both already exist and handle shadow's `blurRad`, `dist`, `dir` attributes.
- `src/pptx/dml/line.py` -- `LineFormat` pattern: wraps parent element, provides `.color` via `lazyproperty`, delegates to `FillFormat`. Good pattern reference for format objects.
- `src/pptx/dml/fill.py` -- `FillFormat` pattern: class method `from_fill_parent()` creates instances with internal `_Fill` delegation. Shows how API objects wrap XML.
- `tests/dml/test_effect.py` -- Existing test uses `Describe` class pattern with parametrized fixtures. Uses `element()` and `xml()` from `tests/unitutil/cxml` for compact XML test fixtures.
- `features/dml-effect.feature` -- Existing BDD feature for `ShadowFormat.inherit` getter/setter.
- `features/steps/effect.py` -- Existing BDD steps use `dml-effect.pptx` test file.
- `docs/dev/analysis/shp-shadow.rst` -- Detailed analysis with schema excerpts for `CT_EffectList`, `CT_OuterShadowEffect`, `CT_InnerShadowEffect`, and other effect types.

**Schema key points (from analysis doc):**
```xml
CT_EffectList:
  blur?, fillOverlay?, glow?, innerShdw?, outerShdw?, prstShdw?, reflection?, softEdge?

CT_OuterShadowEffect:
  children: EG_ColorChoice (1 required color child)
  attributes: blurRad(ST_PositiveCoordinate,0), dist(ST_PositiveCoordinate,0),
              dir(ST_PositiveFixedAngle,0), sx(ST_Percentage,100%),
              sy(ST_Percentage,100%), kx(ST_FixedAngle,0), ky(ST_FixedAngle,0),
              algn(ST_RectAlignment,"b"), rotWithShape(xsd:boolean,true)

CT_InnerShadowEffect:
  children: EG_ColorChoice (1 required color child)
  attributes: blurRad, dist, dir (same types as outer)

CT_GlowEffect:
  children: EG_ColorChoice (1 required color child)
  attributes: rad(ST_PositiveCoordinate,0)

CT_ReflectionEffect:
  no children
  attributes: blurRad, stA, stPos, endA, endPos, dist, dir, fadeDir,
              sx, sy, kx, ky, algn, rotWithShape

CT_SoftEdgesEffect:
  no children
  attributes: rad(ST_PositiveCoordinate) [required]
```

**Key constraints:**
1. `ShadowFormat.__init__` currently takes `spPr` (or `grpSpPr`) element -- must stay backward compatible.
2. Effect inheritance is all-or-nothing: `effectLst` absent = inherit, present = explicit.
3. `EG_ColorChoice` pattern for color access on shadow/glow is identical to the one used by `CT_SolidColorFillProperties` and `CT_GradientStop`.
4. `ST_PositiveCoordinate` and `ST_PositiveFixedAngle` simple types already exist in `simpletypes.py`.
5. No new namespace prefixes needed -- all effects use the `a:` namespace.

### Approaches Considered

Add `GlowFormat`, `ReflectionFormat`, `SoftEdgeFormat` classes in the same `effect.py` file. Create OXML element classes in a new `src/pptx/oxml/dml/effect.py`. Wire new format objects from `BaseShape`.

| Criterion | Score | Notes |
|-----------|-------|-------|
| Pattern alignment | + | Matches `line.py`/`fill.py` pattern of format class + oxml module |
| Elegance | + | Natural home for all effect types in single file, moderate size |
| Surface area | + | 5-6 files modified/created, concentrated in dml layer |
| Risk | + | Low -- straightforward property additions, no architecture changes |
| Testability | + | cxml fixtures work well for parametrized tests |
| Reversibility | + | All additions, no existing code removal |

**Pros**: Single-file for all effect format classes mirrors how `fill.py` has all fill types. OXML classes in new `oxml/dml/effect.py` follows `oxml/dml/fill.py` pattern. Keeps ShadowFormat in its current location. Natural extension point for future effect properties.
**Cons**: `effect.py` will grow to ~250-300 lines with four format classes. ShadowFormat constructor signature unchanged (still takes spPr).

#### 2. Separate files per effect type (P = 0.65)

**Description**: Create `src/pptx/dml/shadow.py`, `src/pptx/dml/glow.py`, `src/pptx/dml/reflection.py`, `src/pptx/dml/softedge.py`. Each contains its format class. OXML classes similarly split.

| Elegance | - | Over-engineering for classes with 3-6 properties each |
| Surface area | - | 8-10 new files |
| Risk | + | Low risk per file, but many integration points |
| Testability | + | Easy to test each in isolation |
| Reversibility | + | Delete individual files |

**Pros**: Maximum separation of concerns, easy to find each effect type.
**Cons**: Too many small files. `SoftEdgeFormat` would be ~20 lines. Violates project convention where `fill.py` contains all fill-related formats. Would need to move `ShadowFormat` out of `effect.py` or have it import from `shadow.py`, creating migration complexity.

#### 3. Thin wrapper pattern -- format objects navigate from effectLst (P = 0.72)

**Description**: Instead of ShadowFormat wrapping `spPr`, change it to wrap `effectLst` (or the individual effect element). Create a master `EffectsFormat` that sits between shape and individual effect formats. `shape.effects.shadow`, `shape.effects.glow`, etc.

| Criterion | Score | Notes |
|-----------|-------|-------|
| Pattern alignment | - | Breaks existing `shape.shadow` API (returns ShadowFormat directly) |
| Elegance | + | Cleaner model -- each format wraps its own element |
| Surface area | - | Must change BaseShape, GroupShape, existing tests |
| Risk | - | Breaking API change to `shape.shadow` |
| Testability | + | Easier to unit test individual elements |
| Reversibility | - | Harder to undo API-level changes |

**Cons**: Breaking change to `shape.shadow` API. Existing code `shape.shadow.inherit` would become `shape.effects.shadow.inherit`. The analysis document explicitly specifies `Shape.shadow` returns `ShadowFormat` (line 26 of shp-shadow.rst).

#### 4. ShadowFormat wraps spPr, others wrap effectLst directly (P = 0.78)

**Description**: Keep `ShadowFormat` wrapping `spPr` (backward compatible) but have new format classes (`GlowFormat`, `ReflectionFormat`, `SoftEdgeFormat`) wrap the `effectLst` element directly. All format classes in `effect.py`. Wire `shape.glow`, `shape.reflection`, `shape.soft_edge` from `BaseShape`.

| Criterion | Score | Notes |
|-----------|-------|-------|
| Pattern alignment | ~ | Mixed -- shadow uses one pattern, others use different |
| Elegance | - | Inconsistent wrapping strategy |
| Surface area | + | Same file count as approach 1 |
| Risk | + | No breaking changes |
| Testability | + | Works with existing test patterns |
| Reversibility | + | All additions |

**Pros**: Maximum backward compatibility. No changes to ShadowFormat constructor.
**Cons**: Inconsistent -- ShadowFormat wraps `spPr` while other effect formats wrap `effectLst`. Confusing for developers reading the code.

#### 5. All formats wrap spPr consistently, unified navigation (P = 0.85)

**Description**: All four format classes (`ShadowFormat`, `GlowFormat`, `ReflectionFormat`, `SoftEdgeFormat`) wrap the `spPr`/`grpSpPr` element and navigate down to their specific effect child. This mirrors the existing `ShadowFormat` pattern exactly. Each format knows how to find its element: `spPr -> effectLst -> outerShdw/glow/reflection/softEdge`. OXML classes in new `src/pptx/oxml/dml/effect.py`. All format classes in `src/pptx/dml/effect.py`. Wire from `BaseShape` and `GroupShape`.

| Criterion | Score | Notes |
|-----------|-------|-------|
| Pattern alignment | + | Extends existing ShadowFormat(spPr) convention |
| Elegance | + | Consistent -- all effects navigate from same root |
| Surface area | + | 5-6 files, concentrated changes |
| Risk | + | No breaking changes, natural extension |
| Testability | + | Same cxml fixture pattern as existing tests |
| Reversibility | + | All additions |

**Pros**: All format objects follow identical pattern: wrap `spPr`, navigate to their child element. Maximum consistency. `shape.glow` parallels `shape.shadow` exactly. ShadowFormat constructor unchanged. Properties on ShadowFormat are purely additive (`.inherit` continues to work). OXML `CT_EffectList` element class enables clean navigation.
**Cons**: Slightly deeper navigation chain (spPr -> effectLst -> effect element), but this matches how ShadowFormat already works for `.inherit`.

### Recommendation

**Selected**: Approach 5 -- All formats wrap spPr consistently, unified navigation

**Rationale**:
- Highest confidence (P = 0.85) -- extends proven ShadowFormat pattern
- Maximum consistency -- all four format types work identically
- Zero breaking changes -- ShadowFormat.inherit continues to work unchanged
- Clean OXML layer -- CT_EffectList + individual CT_* elements follow established xmlchemy patterns
- Matches analysis doc specification (`Shape.shadow` returns `ShadowFormat`)
- Test pattern identical to existing `DescribeShadowFormat` tests

### Design Decisions

**All effect format classes wrap spPr/grpSpPr consistently**: Following Approach 5, every format class (ShadowFormat, GlowFormat, ReflectionFormat, SoftEdgeFormat) takes the spPr or grpSpPr element and navigates down to effectLst and then to its specific child. This gives maximum consistency and matches the existing ShadowFormat pattern.

**EG_ColorChoice on shadow/glow uses same ZeroOrOneChoice pattern as CT_SolidColorFillProperties**: This allows direct reuse of `ColorFormat.from_colorchoice_parent()` without any adapter code.

**Read-only properties return None when no effectLst present (inheriting)**: When the effectLst is absent, all property getters return None to indicate the value is inherited and unknown at this level. When effectLst is present but the attribute is absent, the schema default is returned (e.g., Emu(0) for blurRad, 0.0 for dir).

**Setters raise ValueError when no shadow/glow/softEdge element exists**: Rather than silently creating elements (which could break the all-or-nothing inheritance model), setters require the element to already exist.

**CT_SoftEdgesEffect.rad is RequiredAttribute**: Per the schema, `rad` is required on `a:softEdge` (unlike other effect attributes which are optional with defaults).

### Alignment

This implementation follows the patterns established in:
- `src/pptx/dml/effect.py` (existing ShadowFormat) -- same wrapping pattern
- `src/pptx/oxml/dml/fill.py` (CT_SolidColorFillProperties) -- same ZeroOrOneChoice pattern for color
- `src/pptx/oxml/dml/fill.py` (CT_BlipFillProperties) -- same _tag_seq / ZeroOrOne pattern
- `src/pptx/shapes/base.py` (BaseShape.shadow) -- same lazyproperty wiring pattern
